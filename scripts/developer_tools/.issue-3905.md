refactor: decouple _SIZE_MARKER_TIERS from the public get_fallback_tier_label API so custom tier_map callers aren't silently affected by hardcoded local-model labels

## What

Remove the implicit coupling between the module-private `_SIZE_MARKER_TIERS` constant and the public `get_fallback_tier_label(model_name, tier_map)` function in `.github/scripts/llm_labels.py`. This ensures that a caller passing a custom `tier_map` expects the function to use *only* that map's semantics, without silently applying hardcoded size-marker matching.

**Current problem (`llm_labels.py:79-81`):**
```python
for marker, label in _SIZE_MARKER_TIERS.items():
    if label in tier_map.values() and re.search(rf"\b{marker}\b", model_lower):
        return label
```

When a caller supplies a custom `tier_map` whose values happen to include the literal strings `"local-7b"` or `"local-14b"` (with different intended semantics than the hardcoded size-marker check), the function will still match against those labels. The guard `if label in tier_map.values()` only checks that the label exists in the map — it doesn't prevent the hardcoded size-marker regex from being silently applied to a map the caller never asked to have that behavior.

## Why

- **Correctness:** a caller passing a custom `tier_map` expects the function to use *only* that map's semantics. Silently applying hardcoded size-marker matching is surprising, undocumented behavior.
- **Maintainability:** future edits to `_SIZE_MARKER_TIERS` (e.g. adding a new size marker) would silently change behavior for every custom-`tier_map` caller, even ones that never opted into size-marker detection.
- **API clarity:** the docstring for `get_fallback_tier_label` doesn't mention this constraint at all.

## How

1. **Parameterize the size markers.** Add an optional `size_marker_map` parameter to `get_fallback_tier_label`:
   ```python
   def get_fallback_tier_label(
       model_name: str,
       tier_map: dict[str, str] | None = None,
       size_marker_map: dict[str, str] | None = None,
   ) -> str:
       """Derive a tier label from a model name string (e.g. "claude-haiku-4-5-20251001").

       Used when a tier can't be extracted from issue body text but a model name
       is available. Returns ``_DEFAULT_TIER_LABEL`` if the model name doesn't
       name a known tier or size.

       Args:
           model_name: Model identifier.
           tier_map: Custom tier label map (default: LLM_TIER_MAP).
           size_marker_map: Optional map of size markers to labels (e.g.
               {"7b": "local-7b"}). Defaults to the module's built-in
               ``_SIZE_MARKER_TIERS`` when not supplied, preserving today's
               behavior for callers that don't pass a custom tier_map.
       """
   ```

2. **Update the matching logic** so size-marker matching only runs with an explicit map, defaulting to today's behavior when the caller relies on the default `tier_map` too:
   ```python
   if size_marker_map is None:
       size_marker_map = _SIZE_MARKER_TIERS if tier_map is None else {}

   for marker, label in size_marker_map.items():
       if label in tier_map.values() and re.search(rf"\b{marker}\b", model_lower):
           return label
   ```

3. **Update the docstring** to state clearly that size-marker matching is skipped by default for custom `tier_map` callers unless they explicitly opt in via `size_marker_map`.

Note: `get_fallback_tier_label` currently has **no production call sites** — it's only exercised by `tests/test_llm_labels.py`. There's no caller in `create_followup_issues.py` (or elsewhere) to update; if/when a future caller needs size-marker detection with a custom map, it should pass `size_marker_map=_SIZE_MARKER_TIERS` explicitly at that call site.

4. **Update `tests/test_llm_labels.py`:** the existing `test_get_fallback_tier_label_with_custom_tier_map` test (around line 89) uses a custom map whose values (`"fast-model"`, `"slow-model"`) don't collide with `_SIZE_MARKER_TIERS`, so it doesn't currently exercise this bug. Add a new test that does — e.g. a custom `tier_map` whose value is literally `"local-7b"`, checked against a model name containing `"7b"`, asserting no match unless `size_marker_map` is explicitly passed.

## Files Affected

- `.github/scripts/create_followup_issues.py`
- `.github/scripts/llm_labels.py`
- `tests/test_llm_labels.py`

## Constraints

- Must not break existing behavior for callers using the default `tier_map` (`LLM_TIER_MAP`) — size-marker detection (`"7b"` → `local-7b`, `"14b"` → `local-14b`) must keep working by default in that case.
- No new dependencies — stdlib only.
- Out of scope: `_DEFAULT_TIER_LABEL`'s hardcoded `"sonnet"` value — that's a separate concern.

## LLM Tier

**Haiku** — small, additive change to one function (new optional parameter, a few lines of logic, a docstring update) plus one new test. Low risk since the change only affects behavior when a caller passes both a custom `tier_map` and no `size_marker_map`.

## Success looks like

- `get_fallback_tier_label` has a new optional `size_marker_map` parameter with a docstring explaining the default behavior.
- Calling `get_fallback_tier_label(model_name)` (no custom map) behaves exactly as before — all existing cases in `tests/test_llm_labels.py::test_get_fallback_tier_label` still pass unchanged.
- Calling `get_fallback_tier_label(model_name, custom_tier_map)` no longer matches hardcoded size markers unless `size_marker_map` is explicitly passed.
- A new test in `tests/test_llm_labels.py` demonstrates the fixed isolation (custom map with a colliding value no longer triggers a false match).
- `pytest tests/test_llm_labels.py -v` passes.

## Failure looks like

- Existing tests in `tests/test_llm_labels.py` start failing (regression in default behavior).
- A custom `tier_map` with a `"local-7b"`/`"local-14b"` value still matches size markers with no way to opt out.
- No new test added to cover the fixed isolation.
