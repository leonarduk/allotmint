Add vast.ai-hosted LLM (vLLM/SGLang/TGI) as a developer_tools model source

## What

Add a third LLM backend to `scripts/developer_tools/lib/llm_common.py` — alongside the existing `local` (Ollama) and `cloud` (DeepSeek API) sources — that talks to a self-hosted, OpenAI-compatible inference server rented on [vast.ai](https://vast.ai) (e.g. an RTX 4090 instance running vLLM, SGLang, or TGI). This gives the `developer_tools` scripts (`b_create_issue.py`, `c_triage_issues.py`, `i_local_review.py`, `l_pr_review.py`, `o_review_issue.py`, `lib/commit_and_push.py`) a way to run several concurrent issue/PR review or triage calls against a rented GPU instead of serializing them against Ollama or paying per-token cloud rates.

## Why

The current `local`/`cloud` split (`llm_common.py`) only supports one Ollama call at a time or metered DeepSeek API calls. For batch operations — e.g. `c_triage_issues.py` running across dozens of open issues — a rented GPU running a batching-capable inference server (vLLM/SGLang/TGI all expose an OpenAI-compatible `/v1/chat/completions` endpoint) can serve 5–10 concurrent requests far more cheaply than per-token cloud billing, while staying faster than a single local Ollama call. This matches the user's existing preference for cost-driven, DeepSeek-family model usage over Claude/GPT for routine review work.

## How

- Since vLLM, SGLang, and TGI all speak the same OpenAI-compatible chat-completions schema, the new module does **not** need to be engine-specific — model a generic `remote_openai_common.py` (sibling to `ollama_common.py`) that POSTs to a configurable `{endpoint}/v1/chat/completions` with an API key/bearer token, mirroring the shape of `fetch_ollama_review`/`fetch_deepseek_review` (same timeout/error-handling conventions already used in `ollama_common.py`).
- Add `REMOTE` (or similar) to `MODEL_SOURCES` in `llm_common.py`, wire it through `add_model_source_arg`, `prompt_for_model_source`, `describe_model_source`, `validate_model_source`, and `fetch_review`, following the exact pattern already used for `LOCAL`/`CLOUD`.
- New env vars, read the same way `OLLAMA_ENDPOINT`/`OLLAMA_MODEL`/`DEEPSEEK_API_KEY` are read today (and loaded from repo-root `.env` the way `DEEPSEEK_API_KEY` already is): e.g. `REMOTE_LLM_ENDPOINT`, `REMOTE_LLM_MODEL`, `REMOTE_LLM_API_KEY`.
- Document the new option and a basic vast.ai + vLLM setup walkthrough in `scripts/README.md`, next to the existing "model switch" documentation for `o_review_issue.py`. Since the same rented endpoint is meant to serve both the `developer_tools` scripts and interactive use, include a short note on pointing an interactive OpenAI-compatible client (e.g. Kun Desktop's "Custom OpenAI API" provider) at the same `REMOTE_LLM_ENDPOINT` — no code change needed for this, it's a doc-only pointer since such clients already speak the same API.
- Out of scope for this issue: actually provisioning/renting the vast.ai instance, writing the vLLM/SGLang Docker deploy config, or building an "orchestration" layer to farm out N issues to N concurrent GPU requests — this issue is just the client wiring so the scripts *can* point at a rented endpoint. A follow-up issue can add the concurrency/batch-dispatch layer once the client exists.

## Files Affected

- scripts/developer_tools/lib/llm_common.py
- scripts/developer_tools/lib/remote_openai_common.py (new)
- scripts/README.md
- .env.example (if present — add the new `REMOTE_LLM_*` vars alongside `DEEPSEEK_API_KEY`)
- tests/scripts/ (new unit tests for the new lib module, mirroring existing `ollama_common`/`deepseek_review` test coverage)

## Constraints

- No hardcoded pricing or model names: the source advice for this issue named "DeepSeek V4-Pro" and "$0.27/hr" for a 4090 — neither could be verified against current DeepSeek releases or vast.ai's live market pricing, so the implementation must read model name/endpoint from env vars/config, not hardcode a specific model version or cost assumption.
- Must not commit any vast.ai API keys, SSH keys, or endpoint URLs/tokens to the repo; follow the same "loaded from `.env`, never hardcoded" pattern as `DEEPSEEK_API_KEY`.
- Keep the new module engine-agnostic (OpenAI-compatible HTTP client) rather than coupling to vLLM specifically, since SGLang/TGI expose the same API surface and the user may switch engines.
- Follow the existing error-handling conventions in `ollama_common.py` (explicit `URLError`/`HTTPError`/`TimeoutError`/`JSONDecodeError` handling, `SystemExit(1)` on failure) rather than introducing a new error-handling style.
- Do not touch application backend/frontend code — this is scoped entirely to `scripts/developer_tools/`.
- If the rented instance's `/v1/chat/completions` endpoint is reached over the public internet rather than a private network, it must sit behind a tunnel with its own auth (Tailscale, Cloudflare Tunnel, or an SSH tunnel) rather than being bound to a public IP/port — a bearer API key alone on an unencrypted, publicly-reachable port is not sufficient. Document the recommended tunnel approach in `scripts/README.md` alongside the new env vars; do not default to instructions that expose the port directly.

## LLM tier

sonnet — this requires judgment to correctly generalize the existing `local`/`cloud` two-way switch in `llm_common.py` into a three-way one without breaking existing callers, and to design a clean OpenAI-compatible client module against an established but non-trivial pattern (`ollama_common.py`). Not mechanical enough for haiku; not cross-cutting/architectural enough to need opus.

## Value

Medium Value — reliability/cost improvement for the existing AI-assisted developer_tools workflow (cheaper, faster batch review/triage), but it's additive tooling with no user-facing or financial-data blast radius.

## Failure looks like

- A specific model name, price, or vast.ai instance ID gets hardcoded into the client code instead of being configurable
- Secrets (API keys/endpoint URLs) get committed to the repo or logged in plaintext
- The three-way model-source switch breaks the existing `local`/`cloud` CLI flags or interactive prompt for any of the six scripts that share `llm_common.py`
